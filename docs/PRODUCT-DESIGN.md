# 个人 AI 知识库产品设计文档

> 版本：v0.1
> 状态：产品设计基线
> 更新日期：2026-08-20
> 产品代号：Fuxi（暂定）

## 1．一句话定义

一个给个人写作者使用的本地 AI 知识库：用户只需丢入链接、文件或想法，AI 自动沉淀可追溯的笔记和主题结论，并在提问或选题时直接给出可用结果。

它不是更大的收藏夹，而是把零散素材持续「编译」成个人判断和创作行动的系统。

## 2．目标用户与核心问题

### 2.1 目标用户

MVP 只服务一个用户：知识库所有者本人。典型身份是持续收集 AI、产品、技术和商业素材的公众号写作者。

### 2.2 核心问题

- 素材散落在网页、公众号、GitHub、PDF 和临时想法里，收集成本高。
- 收藏后仍需人工整理，时间久了很难定位。
- 多篇资料里的判断彼此分散，每次写作都要重新拼装。
- 现有笔记工具只能被动存取，不能主动给出选题和下一步行动。
- 通用 AI 不掌握个人积累、立场和长期上下文。

### 2.3 产品定位

我做的是一个给个人写作者使用的 AI 原生知识库。它和 Notion、Obsidian 等通用笔记工具不同：核心价值不是存文件，而是由 AI 持续把素材编译成带来源的个人判断，并服务问答与选题。

## 3．产品目标与非目标

### 3.1 MVP 目标

1. 跑通一次完整的 AI 价值流：输入 → 原文留存 → 原子笔记 → 主题编译 → 问答／选题。
2. 用户不需要手工建目录、写摘要、维护索引和寻找关联。
3. 所有 AI 结论可追溯、可检查、可回退。
4. 在本地运行，不要求服务器、部署和数据库运维。
5. 用 14 天真实使用验证产品是否值得继续投入。

### 3.2 MVP 明确不做

- 不做前端界面，以 Codex 或 Claude Code 会话作为交互入口。
- 不做账号、权限、协作和分享。
- 不做云同步和多端一致性。
- 不做数据库、向量库、embedding 和复杂 RAG。
- 不做图片生成、音视频识别和语音输入。
- 不做自动定时抓取、自动推送和周报。
- 不做微信公众号、X 等高反爬渠道的专用抓取适配；无法稳定读取时允许用户提供正文或文件。
- 不做面向公众的商业化能力。

## 4．MVP 功能范围

| 编号 | 优先级 | 功能 | 用户价值 | 完成标准 |
|---|---|---|---|---|
| F01 | P0 | 收录链接、文件和想法 | 随手把资料放进统一入口 | 三种输入均能形成可追踪记录 |
| F02 | P0 | 原文留存与去重 | 保留事实来源，避免重复污染 | 原文不被覆盖；同一内容重复提交不生成第二份主记录 |
| F03 | P0 | AI 原子笔记 | 自动得到摘要、判断、标签和来源 | 每条素材生成结构完整的笔记，想法生成独立想法笔记 |
| F04 | P0 | 索引与双向关联 | 能快速定位相关内容 | 索引可重建；关联双方内容一致且有可解释分数 |
| F05 | P0 | 主题／实体编译 | 把分散笔记变成当前结论 | 满足编译条件时生成或更新 Wiki 页，并记录来源与矛盾 |
| F06 | P0 | 知识问答 | 直接获得基于个人知识的回答 | 回答优先使用 Wiki，并能追溯到笔记和原文 |
| F07 | P0 | 选题建议 | 把知识转成可执行写作动作 | 每个选题包含角度、依据、为什么现在写和下一步 |
| F08 | P0 | 数据校验 | 防止知识库静默损坏 | 能发现缺字段、断链、单向关联和孤立索引项 |

## 5．核心使用场景

### 5.1 收录资料

用户说：「收录这个链接，并告诉我它和库里哪些内容有关。」

系统完成：读取内容 → 保存原文 → 生成原子笔记 → 复用或新增标签 → 计算关联 → 更新相关 Wiki → 重建索引 → 返回处理结果。

### 5.2 记录想法

用户说：「记住这个想法：AI 产品真正的壁垒可能不是模型，而是不断沉淀的个人上下文。」

系统不伪造外部来源，直接生成想法笔记，标明作者为用户本人，再参与关联和主题编译。

### 5.3 查询判断

用户说：「我现在对个人知识库为什么不需要向量库的判断是什么？」

系统先查索引和 Wiki，再按需下钻到原子笔记；若要核对事实才读取原文。回答区分「资料事实」「用户观点」「AI 推断」，并附来源文件。

### 5.4 生成选题

用户说：「基于最近收录的内容，给我 3 个今天能写的公众号选题。」

系统结合已有主题判断、近期新增资料和证据完整度，输出可执行选题，而不是只列宽泛标题。

## 6．产品架构

### 6.1 总体数据流

```text
链接／文件 ─→ 原料层 raw ─→ 单源笔记 ─┐
                                        ├─→ 编译层 wiki ─→ 问答
用户想法 ───────────────→ 想法笔记 ───┘        │          └→ 选题
                                               └─ 新资料触发回织、标记矛盾
```

设计顺序始终从「取」倒推：先保证问答和选题能用，再决定需要怎样的编译页、原子笔记和输入。

### 6.2 进：输入层

| 输入 | MVP 触发方式 | 处理要求 |
|---|---|---|
| 普通网页／GitHub 链接 | 用户在会话中主动提交 | 保存规范化 URL、抓取时间和正文；失败时给出明确原因 |
| 本地 PDF／Markdown／TXT | 用户提交本地文件 | 保留原文件或可复核文本，不静默丢页 |
| 自然语言想法 | 用户在会话中直接表达 | 标记为用户原创，不补造来源 |
| 公众号／X 等受限链接 | 用户主动提交 | 能读则按链接处理；不能读则请求正文或导出文件，不绕过平台限制 |

### 6.3 存：四层结构

| 层   | 建议目录                            | 内容                | 写入规则                    |
| --- | ------------------------------- | ----------------- | ----------------------- |
| 原料层 | `raw/`                          | 网页正文、附件、抓取元数据     | 只新增，不覆盖；作为事实来源          |
| 笔记层 | `notes/`                        | 单源笔记、用户想法         | 一条内容一篇笔记；允许迭代但保留 Git 历史 |
| 编译层 | `wiki/topics/`、`wiki/entities/` | 多条笔记综合出的主题结论和实体档案 | 新资料到来时回织，保留分歧与更新时间      |
| 行动层 | `briefs/`                       | 可执行写作选题           | 必须引用 Wiki 或笔记，不凭空生成     |

根目录的 `INDEX.md` 是生成物，只负责导航，不承载唯一事实。删除后必须能从现有文件重建。

### 6.4 取：两条 MVP 输出流

#### 问答流

问题 → `INDEX.md` 定位 → 读取 Wiki 当前结论 → 必要时读取原子笔记 → 需要核实时读取原文 → 生成带来源回答。

#### 选题流

用户目标／近期素材 → 筛选有观点、有证据、有时效的主题 → 生成选题卡 → 用户决定是否进入写作。

周报流保留为 v0.2 扩展，不进入 MVP。

## 7．信息结构与数据契约

### 7.1 建议目录

```text
self_knowledge_base/
├── AGENTS.md
├── ROADMAP.md
├── INDEX.md
├── docs/
│   └── PRODUCT-DESIGN.md
├── inbox/
├── raw/
├── notes/
├── wiki/
│   ├── topics/
│   └── entities/
├── briefs/
├── templates/
└── scripts/
```

`inbox/` 只做待处理缓冲区，处理完成后的正式事实必须进入其他层；MVP 不把它做成复杂队列系统。

### 7.2 文件命名

- 正式内容文件：`YYYY-MM-DD-slug.md`。
- `slug` 使用稳定、可读的英文或拼音，创建后不因标题微调而改变。
- 原始附件保持原格式，不强塞 frontmatter；原子笔记用 `source_ref` 指向原文，并用 `content_hash` 作为跨层稳定身份。

### 7.3 原子笔记最小字段

```yaml
---
id: note-20260820-001
type: source_note # source_note | idea_note
title: 示例标题
created_at: 2026-08-20T18:00:00+08:00
updated_at: 2026-08-20T18:00:00+08:00
source_type: web # web | github | pdf | text | user_idea
source_ref: raw/2026/08/example.md
source_url: https://example.com
content_hash: 64位SHA-256
tags:
  - ai-native
  - knowledge-base
related:
  - note-20260819-003
status: active
---
```

正文固定包含：一句话结论、核心信息、我的判断、可用场景、证据与限制。`idea_note` 的 `source_ref` 留空，并明确写「来源：用户想法」。

### 7.4 Wiki 页最小字段

```yaml
---
id: topic-personal-knowledge-base
type: topic # topic | entity
title: 个人 AI 知识库
updated_at: 2026-08-20T18:00:00+08:00
source_notes:
  - note-20260820-001
contradictions: []
status: active
---
```

正文固定包含：当前结论、支持证据、反例或矛盾、仍待确认的问题、可用于哪些内容。更新时重写综合结论，但不能删除仍有效的分歧。

### 7.5 选题卡最小字段

每张选题卡至少包含：标题、核心角度、目标读者、为什么现在写、关键证据、来源页、文章结构建议、下一步动作、状态。

## 8．核心处理规则

### 8.1 入库规则

1. 识别输入类型，生成规范化来源标识。
2. 使用规范化 URL 或内容哈希去重。
3. 先保存原料，再做任何 AI 加工。
4. AI 只从实际内容提取信息；读取失败时不得编造摘要。
5. 标签优先复用已有标签，每条笔记建议 3—5 个；无合适标签时才新增。
6. 写入原子笔记后，运行关联、编译、索引和校验。
7. 任一步失败都返回已完成步骤和失败位置，允许安全重跑。

### 8.2 关联规则

- 机械脚本计算候选关联：标签重叠分＋标题关键词重叠分。
- 达到阈值才写入 `related`，同时写入双方，禁止单向关联。
- 关联结果必须可解释，至少记录共同标签或共同关键词。
- AI 可复核候选，但不能把没有证据的「感觉相关」直接写入正式关联。

初始建议分数：共同标签每个 2 分，共同标题关键词每个 1 分，总分不低于 4 分才进入候选。阈值在验证阶段根据误报调整。

### 8.3 编译规则

- 已有主题／实体页命中新资料时，必须回织更新。
- 同一主题累计两条及以上有效笔记，或用户明确要求时，可新建 Wiki 页。
- 资料互相冲突时，不强行合并成单一答案；同时保留双方观点、时间和来源。
- 编译页表达「当前判断」，不是永久真理，必须记录更新时间。

### 8.4 回答规则

- 使用顺序：Wiki → 原子笔记 → 原文。
- 回答必须标明主要来源文件；没有证据时直接说明库内暂无依据。
- 清楚区分事实、用户观点和 AI 推断。
- 不用模型常识悄悄填补知识库空白。

### 8.5 选题规则

一个合格选题必须同时满足：有明确目标读者、有一句话冲突或新意、有至少两条可追溯依据、有可执行下一步。只有标题、没有证据的结果不写入 `briefs/`。

## 9．技术方案

| 层 | MVP 选择 | 原因 |
|---|---|---|
| 交互与语义处理 | 当前使用的 Codex；兼容 Claude Code | 自然语言交互，AI 直接读写 Markdown |
| 内容抓取 | AI 自带网页读取能力＋按渠道适配 | 先覆盖能稳定读取的渠道，不造通用爬虫 |
| 存储 | 本地 Markdown＋原始附件 | 人可读、AI 可读、Git 可 diff，零运维 |
| 机械任务 | Python 3 标准库优先 | 用于扫描、校验、索引、哈希和关联评分 |
| 检索 | `rg`／Python 关键词检索＋索引 | 先用可解释的轻量方案 |
| 版本与回退 | Git | 查看差异、保留历史、支持人工回退 |

依赖原则：标准库能解决就不加包；需要第三方工具时，先核验维护状态、文档、许可证和 AI 熟悉度，再单独决策。

MVP 的确定性工具统一由 `scripts/kb.py` 提供；AI 工作流位于 `.agents/skills/knowledge-base/`。

## 10．非功能要求

- 本地优先：除读取外部链接和调用 AI 外，正式数据默认留在本机。
- 可追溯：每条知识能追到来源，每个选题能追到证据。
- 幂等：同一输入重复处理，不产生重复主记录和重复关联。
- 可恢复：原文不覆盖，加工失败可安全重跑，索引可重建。
- 可观察：每次处理明确输出新增、更新、跳过和失败的文件。
- 可迁移：核心数据是普通文件，不绑定单一 AI、数据库或笔记软件。
- 可维护：先支持个人规模；达到现有方案明确瓶颈后再评估数据库或向量检索。

## 11．异常与边界处理

| 场景 | 预期行为 |
|---|---|
| 网页无法读取 | 不生成假摘要；保留失败记录并提示用户提供正文或文件 |
| 重复提交同一内容 | 返回已有记录，可选择刷新来源，不新建重复主记录 |
| 页面内容更新 | 保存新版本或变更摘要，不静默覆盖旧事实 |
| PDF 无可提取文本 | 明确提示；OCR 不在 MVP 范围 |
| AI 输出缺字段 | 校验失败，不进入正式层；修正后重跑 |
| 关联写入中断 | 校验检测单向关联并支持修复 |
| 新资料与旧结论冲突 | 在 Wiki 的矛盾区并列记录，不自动删除旧观点 |
| 用户要求删除资料 | 先确认具体文件及关联影响，再执行删除与索引修复 |

## 12．成功指标与 14 天验证

### 12.1 核心指标

- 14 天内至少 10 天主动使用，不依赖提醒。
- 至少收录 30 条真实素材或想法。
- 入库成功率不低于 90％；失败均有明确原因，不能静默丢失。
- 至少完成 5 次真实问答，其中 4 次无需手工翻找原资料即可继续工作。
- 至少生成 3 个真正进入写作流程的选题。
- 关键结论来源可追溯率为 100％。
- 重复主记录、原文被覆盖、断链三类严重问题均为 0。

### 12.2 继续投入条件

满足以下三项即可进入 v0.2：

1. 14 天后仍主动使用；
2. 问答或选题至少一项明显节省时间；
3. 用户愿意继续把新素材放入该系统，而不是回到旧收藏方式。

若不满足，先复盘输入摩擦、加工质量和输出价值，不扩渠道、不加 UI。

## 13．实施计划

### 里程碑 0：手动闭环

改动：创建目录、三类模板和 10 条真实样例，用 Codex 手动完成一次入库、编译、问答和选题。

验收：至少 1 条链接、1 个文件、1 条想法贯通全链路；所有输出可追溯；据此冻结字段定义。

### 里程碑 1：机械任务自动化

改动：实现去重、frontmatter 校验、索引生成、关联评分和双向关联脚本。

验收：脚本可重复运行；第二次运行不产生无意义 diff；能检出缺字段、断链和单向关联。

### 里程碑 2：语义工作流固化

改动：建立入库、编译、问答和选题的 AI 工作流规范与模板。

验收：同一组样例连续运行结果结构稳定；失败能定位到具体步骤；所有回答和选题带来源。

### 里程碑 3：14 天验证

改动：只修复真实使用中的 P0 问题，不扩非目标功能。

验收：按第 12 节复盘指标，明确继续、调整或停止。

## 14．MVP 总验收清单

- [ ] 链接、文件、想法三类输入均能入库。
- [ ] 原文先保存且从不被加工结果覆盖。
- [ ] 重复输入不会生成第二份主记录。
- [ ] 原子笔记字段完整，观点和事实能区分。
- [ ] 索引可以从正式文件一键重建。
- [ ] 关联双向、一致且可解释。
- [ ] Wiki 能回织新资料并保留矛盾。
- [ ] 问答优先读 Wiki，并能下钻到来源。
- [ ] 选题包含角度、证据、时机和下一步。
- [ ] 异常不会静默失败，处理过程可安全重跑。
- [ ] 不包含数据库、向量库、服务器、UI、协作和定时周报。
- [ ] 已完成 14 天真实使用复盘。

## 15．后续版本候选

只有通过 14 天验证后才评估：

- v0.2：周报、渠道专用抓取器、标签治理和批量导入。
- v0.3：多入口投递、选题到文章大纲的工作流。
- 更后期：当文件检索出现可复现瓶颈时，再评估 SQLite、全文索引或向量检索。

候选项不是承诺，不提前实现。

## 16．依据文档与归并说明

本设计由以下三份材料合并：

- `07.产品思维：从你天天用的产品里找金矿.md`：提取定位、MVP、非目标和 14 天验证。
- `08.架构思维：从一页纸 MVP 到一份 AI 看得懂的架构.md`：提取进／存／取、四层存储、回织和输出流。
- `09.技术思维：让 AI 帮你选最适合的技术栈.md`：提取本地 Markdown、Python 机械脚本、轻量检索和零运维约束。

三份材料存在版本差异时，以「能跑通最小价值闭环」为准：问答与选题进入 MVP；周报和专用渠道抓取延后；编译层保留，因为没有它就无法把分散素材变成可直接使用的判断。
